# Leaderboard component QA

Run `node tests/qa/web/leaderboard.mjs` from the repository root. The bounded runner builds this fixture immediately before testing the production leaderboard component in Chromium and WebKit, in English and Simplified Chinese, at desktop and small-phone sizes and with 200% text.

The fixture loads no game page or Toy SDK. Requests and submission outcomes are controlled here, saves use `qa-community-seasons-leaderboard-v1:`, each case uses a fresh browser context and a dedicated temporary local origin, and external requests are blocked. Controls in `window.__leaderboardQA` exist only in this test build. Never publish this fixture as the game.

Reports under `results/qa/leaderboard-*` include source/build hashes, checks, browser errors and screenshots. Checks cover name privacy, one-time explicit Join with double-click protection, Not now, read-only viewing/refresh/period changes, no automatic submission before consent, parent-driven automatic submission after consent, platform consent refusal, uncertain submission lockout, stale period responses, late submission results after a new run with the same score, keyboard focus, empty/error states and enlarged-text reachability. Cloud-choice cases cover loading/unavailability, failed opt-out staying open, and saving a choice after a successful score post without posting that score again. After joining, the dialog has no submission control. The fixture simulates a Bilibili cloud preference and completion/submission outcomes outside the dialog; real cloud persistence, cross-client synchronization and automatic submission are covered by the service/integration checks. The component stores no consent in browser storage. Browser emulation is functional/layout evidence only, not native-device performance evidence.
